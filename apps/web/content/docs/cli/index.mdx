The `kovalio` CLI does everything the dashboard does, from your terminal — run the platform, deploy a
project, tail logs, manage domains, and script it all in CI. It's the same binary you use to install and
run Kovalio itself.

<Callout title="Install it first">
This page assumes the `kovalio` command is already on your PATH. If not, see
[Installation](/docs/getting-started/installation) — the short version is `npm i -g kovalio`
(needs Node 22+) or `curl -fsSL https://get.kovalio.nextrium.org | sh` (brings its own Node).
</Callout>

Every command supports `--help`, so when in doubt:

```bash
kovalio --help              # top-level commands
kovalio deploy --help       # flags for one command
kovalio domain add --help   # flags for a subcommand
```

## Log in with a token

The CLI authenticates with a **Personal Access Token (PAT)** — a string that starts with `opsh_pat_`.
You create one in the dashboard, then hand it to `kovalio login`.

<Steps>

<Step>

### Get a token

In the dashboard, open **Settings → Personal Access Tokens** and create one. Copy it — the secret is shown
only once. (You can also mint tokens from the CLI with [`kovalio token create`](/docs/cli/access).)

</Step>

<Step>

### Log in

Running `kovalio login` with no arguments opens that settings page and waits for you to paste the token.
For scripts and CI, pass it directly:

```bash
# Interactive — opens Settings and prompts for a paste
kovalio login

# Non-interactive — pass the token (great for CI)
kovalio login --token opsh_pat_xxxxxxxxxxxx

# Point at a remote instance instead of localhost
kovalio login --token opsh_pat_xxxxxxxxxxxx \
  --api-url https://your-host --dashboard-url https://your-host
```

The token is validated against the API and saved to `~/.kovalio/config.json`.

</Step>

</Steps>

| `kovalio login` flag | Purpose | Default |
|---|---|---|
| `--token <token>` | PAT (`opsh_pat_…`) for non-interactive login. | prompt |
| `--api-url <url>` | API base URL to authenticate against. | `http://localhost:4000` |
| `--dashboard-url <url>` | Dashboard base URL (opened for the paste flow). | `http://localhost:3001` |
| `--context <name>` | Name of the [context](#connection-contexts) to store this login under. | `default` |

<Callout title="Signing out" type="info">
`kovalio logout` removes the stored token from the active context.
</Callout>

## Global flags

These work on every command.

| Flag | Purpose |
|---|---|
| `--json` | Machine-readable JSON output on stdout (data only — no spinners or prose). Ideal for piping into `jq` or consuming from scripts. |
| `--version` | Print the CLI version. |
| `--help` | Show help for the CLI or any command / subcommand. |

```bash
# Human-readable
kovalio project list

# Same data as JSON for scripting
kovalio project list --json | jq '.[].name'
```

## Connection contexts

A **context** is a named connection: an API endpoint, a dashboard endpoint, and the token to use with them.
They let one machine talk to more than one Kovalio instance — say a local install and a production
server — and switch between them without re-authenticating each time.

Contexts live in `~/.kovalio/config.json`. The one marked **current** is what every authenticated command
uses. `kovalio login` writes to the `default` context unless you pass `--context <name>`.

```bash
kovalio context            # list contexts; the active one is starred
kovalio context use prod   # switch the active context to "prod"
```

### Managing contexts

| Command | Purpose |
|---|---|
| `kovalio context` (alias `ctx`) | Show all contexts; the active row is starred. |
| `kovalio context list` (alias `ls`) | List configured contexts. |
| `kovalio context use <name>` | Switch the active context. |
| `kovalio context add <name>` | Create or update a context's endpoints/token. |
| `kovalio context rm <name>` (alias `remove`) | Remove a context (you can't remove the active one). |

Flags for `kovalio context add`:

| Flag | Purpose |
|---|---|
| `--api-url <url>` | API base URL. |
| `--dashboard-url <url>` | Dashboard base URL. |
| `--token <token>` | Personal access token to store. |
| `--use` | Switch to this context immediately after adding it. |

<Callout title="add vs. login" type="info">
`kovalio context add` only writes config — it doesn't check the token. Use `kovalio login` when you want
the token validated against the API before it's saved.
</Callout>

## All commands

Grouped the same way the reference pages are. Each heading links to the page that covers those commands in
full; run `kovalio <command> --help` for the flag list of any one.

### Running & updating — [reference](/docs/cli/run)

Operate Kovalio itself: the local server, the CLI, and the desktop app.

| Command | Purpose |
|---|---|
| `kovalio up` | Run Kovalio as a persistent service (starts on boot, auto-restarts). Ports are dynamic — a busy port is switched automatically. Add `--foreground` for a one-off attached run. |
| `kovalio stop` | Stop the service started by `kovalio up` (won't restart or return on reboot); also clears a stale database lock. |
| `kovalio reset-admin-password` | Reset the local admin login from this machine, without signing in (forgot-password recovery). |
| `kovalio update` | Update the CLI and bundled server to the latest release. |
| `kovalio install` | Download and install the Kovalio desktop app for this OS. |
| `kovalio install cache` | Manage the local download cache (list, verify, clean, path). |
| `kovalio open` | Open the Kovalio dashboard in your browser. |
| `kovalio status` | Show the local service (installed/running, resolved ports) and the active context's API health. |
| `kovalio doctor` | Diagnose the CLI setup (config, active context, runtime). |

### Access & the raw API — [reference](/docs/cli/access)

Who you are, which instance you're talking to, and an escape hatch to any route.

| Command | Purpose |
|---|---|
| `kovalio login` | Authenticate with a Personal Access Token. |
| `kovalio logout` | Remove the stored token from the active context. |
| `kovalio context` (alias `ctx`) | Manage connection contexts — see [above](#connection-contexts). |
| `kovalio token` | Manage personal access tokens (list, create, revoke). |
| `kovalio api` | Make an authenticated request to any Kovalio API route (like `gh api`). |

### Deploying — [reference](/docs/cli/deploy)

| Command | Purpose |
|---|---|
| `kovalio deploy` | Trigger a deployment for the current project. |
| `kovalio deployment` (alias `deployments`) | Manage deployments — list, inspect, redeploy, rollback. |
| `kovalio logs` | View or stream a deployment's logs. |

### Projects, services & domains — [reference](/docs/cli/projects)

| Command | Purpose |
|---|---|
| `kovalio init` | Link the current directory to a project (writes `.kovalio/project.json`). |
| `kovalio project` (alias `projects`) | Manage Kovalio projects. |
| `kovalio service` (alias `services`) | Manage the services in a compose stack (a multi-service project). |
| `kovalio domain` | Manage custom domains, DNS verification, and SSL certificates. |

### Edge & monitoring — [reference](/docs/cli/edge)

The public reverse proxy on `:80/:443` and the traffic it records.

| Command | Purpose |
|---|---|
| `kovalio edge` | Install and manage the OpenResty edge; take over an existing proxy; read traffic, analytics, and request logs. |

### Self-host infrastructure — [reference](/docs/cli/self-host)

| Command | Purpose |
|---|---|
| `kovalio server` | Manage self-hosted SSH servers. |
| `kovalio system` | Instance settings, onboarding, migration, and data transfer. |
| `kovalio mail` | Self-hosted mail server (iRedMail) setup and admin. |
| `kovalio backup` | Manage backups — policies, runs, restores, and destinations. |
